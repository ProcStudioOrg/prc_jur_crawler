## 0b. 🔴 HTTP 000 NÃO É PORTAL FORA DO AR — E AQUI ELE VARIA POR HOST NO MESMO TRIBUNAL

`curl https://tcjuris.tce.mg.gov.br/` devolve **000**, exatamente como o e-SAJ morto do TJBA.
**Não é queda.** Medindo em camadas (a lição do TJPE):

| Camada | tcjuris / mapjuris / dadosabertos | www.tce.mg.gov.br |
|---|---|---|
| DNS | resolve (177.125.90.199 / .206) | resolve |
| TCP 443 | **abre** | abre |
| TLS | handshake completa, **cadeia INCOMPLETA** | handshake completa, cadeia **completa** |
| `openssl` | `Verify return code: 21 (unable to verify the first certificate)` | `Verify return code: 0 (ok)` |
| HTTP com verificação | **000** | **200** |
| HTTP com `-k` | **200** (84.655 bytes) | 200 |

🔴 **A NOVIDADE EM RELAÇÃO AO TJPE: o defeito é POR HOST, dentro do MESMO tribunal e com o
MESMO certificado curinga.** É o mesmo `*.tce.mg.gov.br` (Sectigo, emitido 22/06/2026) nos
quatro hosts; `www` manda o intermediário e `tcjuris`/`mapjuris`/`dadosabertos` **não mandam**.
Quem medisse só o `www` concluiria "o TLS do TCE-MG está bom" e o crawler quebraria só no host
que importa. **Meça o TLS do host do módulo, não o do institucional.**

✅ **A correção é fornecer o intermediário, NÃO desligar a verificação** (a receita do TJPE):

```
AIA do certificado folha:
  http://crt.sectigo.com/SectigoPublicServerAuthenticationCAOVR36.crt
  (CN = Sectigo Public Server Authentication CA OV R36)

Provado:  curl --cacert <raízes + intermediário>  →  HTTP 200
          curl com as raízes do sistema sozinhas  →  HTTP 000
```

O navegador não sofre porque busca o intermediário sozinho pelo AIA; `curl` e Node não.

## 1. Busca principal (query) — `txtAssunto`

Campo de texto livre, com autocomplete de tesauro (`POST /Home/BuscarTesauro`, a cada tecla).

```html
<input type="hidden" id="txtAssuntoOriginal" name="txtAssuntoOriginal" />
<input tabindex="14" type="text" id="txtAssunto" autocomplete="off"
       onkeyup="ShowHideRestricoes(this.value);" onblur="ShowHideRestricoes(this.value);"
       name="txtAssunto" />
```

🔴 **O TERMO SOZINHO NÃO BUSCA — é preciso marcar ao menos uma "restrição".** Se `txtAssunto`
está preenchido e nenhum `chxRestricoes` está marcado, `BuscaRegistros()` mostra
*"Favor informar no mínimo uma restrição de pesquisa."* e **retorna sem emitir requisição
nenhuma**. Foi o que aconteceu na primeira tentativa deste mapeamento: a busca "rodou" e não
houve XHR. ⚠️ E os três checkboxes nascem `disabled`: só habilitam no **`keyup`** do campo —
`page.fill()` do Playwright não os habilita, `page.type()` sim.

🔴 **O PORTAL TRANSLITERA CARACTERES ANTES DE ENVIAR — contrato inédito no repo.** Em
`Decisoes.js`, antes do POST:

| Caractere digitado | Vai no fio como |
|---|---|
| `"` (aspas) | `◕` (U+25D5) |
| `%` | `☻` (U+263B) |
| `(` | `↑` (U+2191) |
| `)` | `↓` (U+2193) |

Um crawler que mandasse aspas ou parênteses crus **não estaria falando a mesma língua que o
formulário**. Nenhum outro tribunal do repo faz isso.

⚠️ Há ainda um validador próprio de stemming: `POST /Home/VerificaStem` com `assunto=<termo>`
→ `{"sucesso":false}` quando o termo é aceitável (`sucesso:true` traz mensagem de recusa).

### Operadores anunciados (NÃO TESTADOS — a busca nunca respondeu)

A tela imprime a legenda: **`E`   `Ou`   `%`   `Não`   `(`   `)`**. ⚠️ O `%` aparecer na
legenda combina com a transliteração `%` → `☻`, sugerindo que ele é o **curinga** do portal.
**Nada disso foi medido** — o repo já pegou legenda mentirosa em TJPI, TJBA e TCE-PR.

## 5. Datas — dois eixos reais

```html
<input id="dp11"     name="dp11"     data-date-format="dd/mm/yyyy" />  <!-- sessão, início -->
<input id="dp22"     name="dp22"     data-date-format="dd/mm/yyyy" />  <!-- sessão, fim -->
<input id="dpPub11"  name="dpPub11"  data-date-format="dd/mm/yyyy" />  <!-- publicação, início -->
<input id="dpPub22"  name="dpPub22"  data-date-format="dd/mm/yyyy" />  <!-- publicação, fim -->
```

✅ **Dois eixos distintos: data da SESSÃO e data da PUBLICAÇÃO** — como TCE-SP, e diferente
de TCE-RS (só sessão) e TCE-RJ (só voto). Formato **DD/MM/YYYY**.

⚠️ **Meia janela é recusada no CLIENTE**: preencher só uma ponta dá *"Favor preencher a data
inicial e a data final…"* e a busca não sai. Isso é validação de tela — **não prova nada
sobre o servidor**, que é onde TJPI/TJRR/TCE-PR falharam. Não medido.
Validadores próprios: `POST /Home/ValidarData/` e `POST /Home/DataMaior/`.

## 7. 🔴 O BLOQUEIO — reCAPTCHA v2, e ele é VERIFICADO NO SERVIDOR

```
sitekey: 6Lf11kAUAAAAAPYx2uvLlBtMuTXz7JD5ovQYOeSg   (reCAPTCHA v2 "checkbox", size=normal)
```

Fluxo real, lido em `Decisoes.js` e confirmado ao vivo: antes de montar o grid,
`BuscaRegistros()` chama `POST /Home/VerificarCaptchaPreenchido`; se a resposta for falsy,
abre o modal e **não busca**.

### A prova de que o portão é do SERVIDOR, não da tela

A lição do TJBA é que captcha protege a tela e não o endpoint, e a do TJSE é que
`grep turnstile` não prova nada — **o que prova é mandar a requisição e ler a resposta**.
Foi o que se fez, em três medições:

| Teste | Resultado |
|---|---|
| `POST /Home/Busca` cru (sem sessão), com todos os campos do formulário | HTTP **200** com **5.399 bytes** = página *"Ocorreu um erro..."*, **não** o grid |
| `POST /Home/Busca` com **sessão viva do Playwright** (`ASP.NET_SessionId` real), captcha **não** resolvido, disparado de dentro da própria página | HTTP **200**, **5.392 bytes**, mesma página de erro |
| `POST /Home/VerificarCaptchaPreenchido` com a mesma sessão viva | HTTP 200 com **corpo vazio** (falsy) |
| Busca no navegador, com termo e restrição corretos | modal **"Favor Informar o captcha"**, `grid1` com **0 bytes** |

🔴 **Ou seja: sessão válida não destrava.** O flag de captcha é de servidor, e sem ele
`/Home/Busca` devolve página de erro **com HTTP 200** — mais uma casca de 200, e das ruins,
porque um crawler que só olhasse `res.ok` gravaria "busca respondeu".

⚠️ **E há um WAF F5 BIG-IP por cima**: `POST /Home/VerificarCaptchaPreenchido` **de fora do
navegador** devolve **HTTP 403 "Request Rejected — Your Support ID is 14225693770523235543"**,
enquanto de dentro da página devolve 200. Cookies `BIGipServer*` e `TS*` confirmam o F5.
São **dois** mecanismos distintos: o WAF (que reage ao cliente) e o captcha (que reage à
ausência de token). Não confunda um com o outro ao diagnosticar.

### Qual dos quatro tipos de bloqueio é este

O repo já catalogou: script bloqueado (TJPB), negação na borda sem challenge (TJRN), desafio
interativo visível (STJ), widget que roda e não emite token (TJSE). **Este é um quinto caso
diferente: reCAPTCHA v2 de checkbox que carrega normalmente e é conferido por FLAG DE SESSÃO
no servidor.** Não foi testado se ele passaria com IP residencial — mas, ao contrário do
Turnstile do TJSE, aqui **nem se chega a pedir token**: o servidor simplesmente nega a busca
enquanto a sessão não estiver marcada como aprovada. Este repo não resolve captcha.
