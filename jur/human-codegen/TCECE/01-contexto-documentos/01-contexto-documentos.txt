```

Content-Type: application/json
User-Agent: <OBRIGATÓRIO — ver ressalva 🔴 nº 2>

{
  "texto": "nepotismo",
  "filtros": null,             // array de cláusulas Elasticsearch cruas, ou null
  "searchAfterSort": null,     // cursor: o campo `sort` do último doc da página anterior
  "buscaPalavraExata": false,
  "buscaPesquisaExata": false,
  "sort": "desc"
}
```

Resposta:

```json
{ "erros": [],
  "data": { "tempo": 57, "tamanho": 2127, "lista": [ {...10 docs...} ],
            "agregacao": { "group_by_idtipodocumento": {"buckets":[...]},
                           "group_by_nrprocesso": {"buckets":[...]},
                           "sample": {...} } } }
```

Sem cookie, sem CSRF, sem ViewState, sem captcha (`window.grecaptcha` e `window.turnstile`
são `undefined` na tela — medido no Playwright). Latência 0,4–3 s.

# Ferramentas Comuns

## 1. Busca principal (query)

Campo único `input[type=search]`, placeholder **"O que você está procurando?"** → vira o
campo `texto` do JSON. Espaço = **E implícito** (provado: `nepotismo` 2127 →
`nepotismo licitacao` 1217; e `nepotismo ZZQQINVENTADO` = **0**, o que prova que é AND e
que não há normalização mágica engolindo termo desconhecido).

```html
<!-- ver 01-barra-busca.html -->
<input type="search" class="searchbar-input" placeholder="O que você está procurando?">
```

Prints: `01.01-tela-inicial.png`, `01.02-termo-preenchido.png`

## 2. Operadores — **nenhum funciona** (medido termo a termo)

A tela exibe os botões `E`  `OU`  `NÃO`  `" "` sob o rótulo **"OPERADORES LÓGICOS"**.
Todos são inertes: viram palavra comum e o Elasticsearch as descarta como stopword.

| Termo enviado | `tamanho` |
|---|---|
| `nepotismo` | 2127 |
| `nepotismo licitacao` | **1217** |
| `nepotismo E licitacao` | **1217** |
| `nepotismo OU licitacao` | **1217** |
| `nepotismo NÃO licitacao` | **1217** |
| `nepotismo NAO licitacao` | **1217** |
| `nepotismo ZZQQINVENTADO` | 0 |

| Operador | Funciona? | Observação |
|---|---|---|
| `E` | ❌ | idêntico ao espaço (1217) — o AND já é implícito |
| `OU` | ❌ | **devolve a interseção (1217), não a união.** `A OU B` *restringe* |
| `NÃO` / `NAO` | ❌ | idêntico ao AND — **não exclui nada** |
| `ADJ` / `PROX` | ❌ | não existem (não oferecidos e não testados como sintaxe própria) |
| `$` | ❌ **não é curinga** | `nepotism$` = **14** (contra 2127 de `nepotismo`) |
| `*` | ❌ **não é curinga** | `nepotism*` = **31** |
| `"frase exata"` | ⚠️ **não provado** | ver ressalva 🔴 nº 4 |

🔴 O `$`/`*` são o caso perigoso: **não zeram**, devolvem 14 e 31 julgados de verdade. Quem
usar lê "o curinga funcionou, o acervo é pequeno" — e perde 98% da base.

## 3. Acento e caixa — **normalizados de forma agressiva** (oposto do TCE-PE)

| Par | Contagem |
|---|---|
| `nepotismo` / `nepotísmo` (acento **errado**) | 2127 / **2127** |
| `servidão` / `servidao` | 1476 / **1476** |
| `inelegibilidade` / `inelegibilidádé` (acentos inventados) | 8949 / **8949** |

✅ O acento é **removido**, não só normalizado — acento errado dá o mesmo resultado que o
certo. O crawler **não precisa** normalizar a query. **É o inverso exato do TCE-PE**, onde
`licitacao`=40 contra `licitação`=13.636.

⚠️ Mas **palavra curta e comum devolve 0**: `texto:"a"` = **0**, `texto:"de"` = **0**.
Zero aqui é stopword, não ausência de acervo.

## 4. Filtros — cláusulas Elasticsearch cruas no array `filtros`

O SPA monta `filtros` como **query DSL literal** (no módulo sistematizado ele empurra
`{term:{tesauro_termo_nome: X}}`). Ou seja: o campo aceita `term`, `match`, `range`…
Medidos e **provados por contagem**:

| Filtro | Efeito medido |
|---|---|
| `{"term":{"idtipodocumento":"4"}}` (ACÓRDÃO) | `nepotismo` 2127 → **64** ✅ |
| `{"term":{"idtipodocumento":"999999"}}` | **0** ✅ (id inválido **não** é ignorado — bom) |
| `{"range":{"dtfinalizado":{"gte":"2024-01-01","lte":"2024-12-31"}}}` | 2127 → **169** ✅ |
| idem 2025 | 2127 → **139** ✅ |
| `{"term":{"nrprocesso":"40717/2019-6"}}` | **100** documentos daquele processo ✅ |
| `{"match":{"nrprocesso":"..."}}` | idêntico ao `term` (100) |

Tanto `"4"` (string) quanto `4` (número) funcionam em `idtipodocumento`.

## 6. Paginação — `searchAfterSort` (Elasticsearch `search_after`)

Página fixa de **10** documentos (não há parâmetro de tamanho no contrato do SPA — **não
testado se a API aceita um; pendência**). Cada documento traz o campo `sort`:

```
"sort": [1782432000000, "9535433"]     // [epoch ms de dtfinalizado, iddocumento]
```

Para a página seguinte, envie esse array em `searchAfterSort`. **Medido:**

| `searchAfterSort` enviado | resultado |

## 7. Total: **exato até 10.000, saturado a partir daí**

`tamanho` trava em **10000** — teto clássico do Elasticsearch (`track_total_hits`).

| Termo | `tamanho` |
|---|---|
| `""` (vazio, base inteira) | **10000** ← saturado |
| `contrato`, `licitacao`, `prescrição` | **10000** ← saturado |
| `inelegibilidade` | 8949 (exato) |
| `nepotismo` | 2127 (exato) |
| `a`, `de`, `ZZQQINVENTADO` | 0 |

✅ **Prova de que abaixo de 10.000 é exato:** os 82 buckets de
`agregacao.group_by_idtipodocumento` de `nepotismo` **somam exatamente 2127**, o mesmo
`tamanho`. A partição fecha.

🔴 Consequência: **o tamanho real da base é desconhecido** — `texto:""` satura. O crawler
tem de classificar todo total ≥ 10000 como *saturado*, nunca como exato.
