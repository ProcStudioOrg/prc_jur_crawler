## 🔴 Cadeia TLS incompleta — HTTP 000 que NÃO é "fora do ar"

`proinfo.tce.ba.gov.br` (e `sistemas.`) apresentam SÓ o certificado folha
(`CN=*.tce.ba.gov.br`, emitido por `Sectigo Public Server Authentication CA OV R36`)
e OMITEM o intermediário. Medido em camadas:

   DNS      → 187.44.199.52 e 189.112.186.52 (dois nós)
   TCP 443  → ABRE
   TLS      → "TLS alert, unknown CA (560) / unable to get local issuer certificate"
   curl     → HTTP 000

⚠️ E o `www.tce.ba.gov.br` — MESMO certificado curinga — responde 200 normalmente,
porque o `www` MANDA o intermediário e o `proinfo` não. Quem medisse só o
institucional concluiria que o TLS do tribunal está bom. **É o TCE-MG de novo, com a
mesma CA (Sectigo OV R36) e o mesmo desfecho.**

✅ Correção: fornecer o intermediário pelo AIA do próprio certificado
   (http://crt.sectigo.com/SectigoPublicServerAuthenticationCAOVR36.crt),
   **NÃO** desligar a verificação. Provado: 000 → 400/200 com `rejectUnauthorized`
   ainda ligado. O PEM está embutido em `src/TCEBANavigator.js`.

## 1. Busca principal (query)

Campo: `<input type="text" name="termo" id="termo">`   → API: `termo`
Rótulo da tela: "Pesquisa textual"
Texto do portal: "A pesquisa identifica as ocorrências no conteúdo das ementas, das
                  decisões e dos votos dos relatores".

🔴 NÃO HÁ PAGINAÇÃO, E `qtRegistros` É UM LIMIAR QUE RECUSA — achado central.
   O portal manda `qtRegistros=200`. Quando a busca casa mais que isso o servidor
   devolve **HTTP 400** com corpo

     {"negocioException":"br.gov.ba.cedasc.api.exception.NegocioException",
      "message":"A sua pesquisa retornou mais de 200 ocorrências. Por favor, refine
                 o seu critério de pesquisa utilizando outros campos de filtro
                 disponíveis."}

   e **ZERO documento** — não uma primeira página. E o número da mensagem **ECOA o
   valor pedido**: com `qtRegistros=1000` ele diz "mais de 1000 ocorrências". Ou seja
   **o teto é escolha do cliente, não limite do servidor**. Medido:

     termo=licitação  qtRegistros=200    → HTTP 400, 0 documentos
     termo=licitação  qtRegistros=2000   → HTTP 200, 1879 documentos (88 s)
     termo=licitação  qtRegistros=5000   → HTTP 200, 1879 documentos (107 s)
     termo=licitação  qtRegistros=20000  → HTTP 200, 1879 documentos (83 s)

   ✅ O total é **EXATO**, não saturado: 1879 nas três medições.
   O crawler manda 5000 por default e, se ainda assim estourar, FATIA POR ANO.

⚠️ A API é LENTA: 38–110 s por busca larga. Não é bloqueio.

## 2. Operadores — 🔴 NÃO EXISTE NENHUM, e o termo é casado como FRASE

Base de comparação: `nepotismo` = 7, `súmula` = 975.

     nepotismo E súmula      → 0
     nepotismo AND súmula    → 0
     nepotismo súmula (espaço)→ 0        🔴 o espaço NÃO é AND nem OR
     nepotismo OU súmula     → 0
     nepotismo OR súmula     → 0
     nepotismo NAO súmula    → 0
     nepotismo NOT súmula    → 0
     "frase exata" (aspas)   → **HTTP 500**  🔴 as aspas DERRUBAM a busca

✅ MAS O TERMO DE DUAS PALAVRAS FUNCIONA — quando é uma FRASE REAL do texto:
     de nepotismo            → 4
     prática de nepotismo    → 2
     nepotismo cruzado       → 0   (frase que não ocorre)

🔴 A LIÇÃO — O `termo` É UMA FRASE LITERAL, NÃO UMA LISTA DE PALAVRAS. Este é o
   primeiro portal do repo em que **todo operador zera E o espaço também não é
   conectivo**. Não é "os ingleses funcionam e os portugueses não" (TJBA/TJES) nem o
   inverso (TJPE): **não há conectivo nenhum**, porque a string inteira é casada como
   sequência contígua. Por isso `nepotismo súmula` = 0 e `de nepotismo` = 4 — a
   diferença não é o número de palavras, é se aquela sequência EXISTE no texto.
   **Esse zero NÃO é ausência de jurisprudência sobre os dois temas**: quem quiser
   cruzar dois conceitos tem de rodar duas buscas e interseccionar no cliente.
   ⚠️ E as aspas, que em todo outro tribunal do repo são o recurso que sobra quando os
   operadores falham, aqui são a única coisa que produz **HTTP 500** — apesar de a
   busca já ser por frase, o que tornaria as aspas redundantes de qualquer modo.

✅ O CASAMENTO É POR PALAVRA INTEIRA, E O `*` É CURINGA DE VERDADE — provado pelo par:
     nepotism    → 0     (prefixo truncado não casa: não é substring)
     nepotismo   → 7
     nepotism*   → 7     (o curinga recupera exatamente o que o truncamento perdeu)
   ⚠️ Já o `$` **zera**: `nepotism$` → 0. Não é curinga aqui.

✅ ACENTO É NORMALIZADO — não avise sobre acento:
     termo=licitacao  anoDecisao=2024 → 125
     termo=licitação  anoDecisao=2024 → 125

## 14. Número do processo  🔴 CASA POR SUBSTRING

Formato: `TCE/<sequencial 6 dígitos>/<ano>` — ex. `TCE/000405/2025`.
🔴 NÃO há número CNJ (contas não é Judiciário): `src/cnj.js` reprovaria todo processo
   válido, e o DataJud não cobre.

Parâmetros: `numeroProtocolo` + `anoProtocolo`. Medido:

     numeroProtocolo=000405 & anoProtocolo=2025  → 2, todos de TCE/000405/2025    ✅
     numeroProtocolo=TCE/000405/2025 (máscara)   → 2, idem (a máscara é aceita)   ✅
     numeroProtocolo=405    & anoProtocolo=2025  → 6, de TCE/000405/2025,
                                                    TCE/003405/2025,
                                                    TCE/004050/2025              🔴
     numeroProtocolo=000405 SEM ano              → 13, de 2001, 2002, 2004…      🔴
     numeroProtocolo=999999 & anoProtocolo=2025  → 0   (honrado, não ignorado)    ✅

🔴 A LIÇÃO: o campo casa por **substring**, e o sintoma é um número PLAUSÍVEL, não um
   erro. Mandar o sequencial sem os zeros à esquerda arrasta processo alheio com HTTP
   200 e cards válidos. O `TCEBAChecker` (a) normaliza para 6 dígitos e (b) **confere
   no cliente** que o `numeroProtocolo` devolvido é exatamente o pedido, descartando o
   resto e avisando quanto caiu.
